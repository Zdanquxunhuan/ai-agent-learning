# 企业级知识库问答系统（RAG）需求说明

## 1. 项目目标

构建一个基于 Java 17 和 Spring Boot 的企业级知识库问答系统。

用户上传文档后，系统能够解析文档、切分文本、生成向量并建立索引。用户提问时，系统检索相关内容，基于检索证据生成答案，并返回可追溯的引用来源。

当检索不到足够证据时，系统应拒绝回答，避免编造内容。

本文档定义 V1 版本的目标需求，不代表相关功能已经全部实现。

## 2. 用户类型

### 2.1 普通用户

- 上传支持的文档。
- 查看自己有权访问的文档及其处理状态。
- 针对有权访问的知识库提出问题。
- 查看回答内容和引用来源。

### 2.2 系统维护者

- 配置应用、数据库和模型服务。
- 查看运行状态及必要的错误日志。
- 处理文档解析、索引和模型调用失败等问题。

V1 暂不提供独立的管理员管理后台。

## 3. 支持的文件类型

| 文件类型 | 支持范围 | 限制 |
| --- | --- | --- |
| TXT | UTF-8 文本文件 | 空文件应被拒绝或识别为无有效内容 |
| PDF | 可提取文本的 PDF | 暂不实现 OCR |
| DOCX | Word 文档 | 无法解析的文档应返回可诊断错误 |

其他不支持的文件类型应被拒绝。

系统应校验文件类型、文件大小和空文件等情况。文件名不能直接决定服务器上的存储路径。

## 4. 功能需求

### 4.1 文档上传

输入：
- 上传的文件。

输出：
- 文档 ID（documentId）。
- 原始文件名。
- 文档处理状态。
- 文件内容哈希值（contentHash）。

验收条件：
- 合法文件可以成功登记。
- 空文件、非法类型和超出大小限制的文件会被拒绝。
- 文件元数据能够持久化保存。
- 恶意文件名不能控制服务器存储路径。

### 4.2 文档解析与索引

输入：
- 已登记的文档及其内容。

处理：
- 解析文档文本。
- 将文本切分为多个 Chunk。
- 为后续 Embedding 和向量检索准备数据。

输出：
- 文档对应的文本片段。
- 文档处理状态。
- 可追踪的失败信息。

验收条件：
- 成功处理的文档最终进入 READY 状态。
- 处理失败的文档进入 FAILED 状态。
- 文档片段能够追溯到原始文档及其来源位置。
- 处理失败时能够定位原因。

### 4.3 知识库问答

输入：
- 用户提出的问题。

处理：
- 检索用户有权访问的相关文档片段。
- 根据检索证据组织答案。
- 校验引用来源。

输出：
- 回答内容。
- 引用来源。
- 必要时返回证据不足或处理失败的原因。

验收条件：
- 回答能够关联到实际检索到的证据。
- 引用可以追溯到原始文档。
- 不得引用本次检索结果中不存在的片段。

### 4.4 证据不足时拒答

输入：
- 无法检索到相关证据，或证据不足的问题。

输出：
- 明确的拒答结果及原因。

验收条件：
- 无相关证据时，不得伪造确定性答案。
- 不得生成虚假的引用。
- 能区分无检索结果、证据不足和模型调用失败等情况。

### 4.5 文档权限隔离

输入：
- 当前用户身份及其查询请求。

处理：
- 根据服务端的用户身份和文档访问权限过滤检索结果。

输出：
- 仅包含当前用户有权访问的文档内容。

验收条件：
- 用户 A 不能检索、引用或删除用户 B 无权访问的文档。
- 不得仅根据请求体中的 userId 判断访问权限。
- 未授权文档的内容不能通过回答或引用泄漏。

## 5. 文档状态要求

V1 定义以下文档状态：

- UPLOADED：文档已上传并登记。
- PROCESSING：文档正在解析和索引。
- READY：文档处理完成，可以参与检索。
- FAILED：文档处理失败。

预期状态流转：

UPLOADED → PROCESSING → READY

UPLOADED → PROCESSING → FAILED

具体字段、状态转换规则及异常处理方式在数据模型设计阶段进一步明确。

## 6. V1 非目标

首版暂不实现以下功能：

- PDF 图片 OCR。
- 图片内容理解及多模态问答。
- 复杂的多 Agent 协作流程。
- 必须依赖消息队列的分布式异步架构。
- 独立的管理员管理后台。
- 完整的企业级单点登录和复杂角色管理系统。

后续是否增加这些能力，根据实际需求和测试结果决定。

## 7. 技术与实现约束

- Java 17。
- Spring Boot 3.x。
- Maven。
- PostgreSQL 和 Flyway。
- pgvector 向量存储。
- LangChain4j 作为大模型应用集成方案。
- 使用 Fake adapter 隔离外部模型服务依赖，保证核心逻辑可独立测试。
- 敏感配置通过环境变量等配置机制提供，不将真实密钥提交到 Git。

具体依赖版本和架构取舍以项目实际配置及 ADR 记录为准。

## 8. 整体验收原则

- 每项功能都有明确的输入、输出和验收条件。
- 核心功能具有对应的自动化测试。
- 异常场景能够被识别和追踪。
- 文档权限和引用校验具有可验证的测试证据。
- 文档、架构图和实际代码保持一致。

本项目定位为可复现、可测试的作品集项目，不预先宣称达到生产环境合规要求或生产级 SLA。
